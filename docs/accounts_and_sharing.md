# إدارة الحسابات ومشاركة التحكم مع العائلة (Accounts & Sharing)

يوضح هذا المستند الخيارات المتاحة لمشاركة التحكم في مشترك الفيشة الذكي مع أفراد العائلة أو زملاء العمل مع تحديد الصلاحيات (صلاحيات كاملة للمسؤول، وصلاحيات للمشاهدة فقط أو تحكم مقيد لباقي الأفراد).

---

## 1. الخيارات المعمارية المتاحة

### أ) حساب موحد للجميع (Same Server Login)
- **طريقة العمل**: يدخل جميع أفراد العائلة بنفس اسم المستخدم وكلمة المرور الخاصة بسيرفر MQTT أو الاتصال المحلي.
- **المميزات**:
  - لا يتطلب أي تعديل في السيرفر أو التطبيق أو الفيرموير.
  - إعداد فوري وبسيط.
- **العيوب**:
  - غياب تام لتحديد الصلاحيات: يستطيع أي فرد إطفاء أي مخرج (حتى الحساسة مثل الراوتر)، أو تعديل الجداول والأتمتة، أو حذف المشتركات بالخطأ.
  - في حال الرغبة في إلغاء صلاحية شخص، يجب تغيير كلمة المرور في كل الأجهزة.

---

### ب) حسابات مستخدمين منفصلة على سيرفر EMQX مع قواعد ACL (موصى به ⭐)
- **طريقة العمل**: يمتلك سيرفر EMQX وسيط MQTT نظام مصادقة (Authentication) ونظام تحكم في الوصول (Access Control Lists - ACL). يتم إنشاء مستخدم لكل فرد من أفراد العائلة، مع تطبيق قواعد ACL تمنع المستخدمين العاديين من النشر (Publish) على مواضيع الأوامر (`mttl/<hub>/cmd`)، وتسمح لهم فقط بالاشتراك (Subscribe) لمتابعة الحالة وقراءة البيانات.
- **المميزات**:
  - أمان فائق واعتماد على معايير MQTT القياسية.
  - لا يتطلب تغيير كود الفيرموير في ESP32 (يبقى خفيفاً ومستقراً).
  - إمكانية منح صلاحيات متدرجة (مشاهدة فقط، أو تحكم في مخارج محددة دون غيرها).
  - سهولة إضافة أو إلغاء حسابات العائلة من لوحة تحكم EMQX في أي وقت.
- **العيوب**:
  - يتطلب وسيط MQTT يدعم ACL (مثل EMQX وهو المستخدم حالياً).

---

### ج) إدارة الأدوار ورمز PIN داخلياً في الفيرموير (Hub-Side PIN/Roles)
- **طريقة العمل**: يتم تخزين مستخدمين أو أرقام PIN داخل ذاكرة ESP32 (NVS)، ويتم تمرير الرمز مع كل طلب HTTP أو أمر MQTT للتحقق منه.
- **المميزات**:
  - يعمل محلياً حتى في حال انقطاع اتصال السيرفر الخارجي.
- **العيوب**:
  - استهلاك لموارد ESP32 المحدودة (ذاكرة RAM و Flash).
  - تعقيد كبير في كود الفيرموير وإمكانية ظهور ثغرات برمجية.
  - صعوبة استعادة التحكم إذا نُسي رمز الـ PIN الرئيسي.

---

### د) خادم وسيط سحابي مع Firebase Auth (Cloud Backend + Firebase)
- **طريقة العمل**: إنشاء خادم وسيط (Node.js / Go) يتولى مصادقة المستخدمين عبر Firebase Auth، ويحتوي على قاعدة بيانات للأدوار، ثم يقوم الخادم الوسيط بإرسال الأوامر إلى الـ Hub.
- **المميزات**:
  - واجهات تسجيل دخول متقدمة (Google / Apple / Phone Auth)، وإدارة أدوار احترافية.
- **العيوب**:
  - تكلفة إضافية للبنية التحتية والسيرفر السحابي.
  - زيادة زمن الاستجابة (Latency).
  - فقدان ميزة التحكم المباشر الخفيف.

---

## 2. الخيار الموصى به: EMQX مع قواعد ACL

نوصي باعتماد **الخيار (ب)** لأنه يستغل الإمكانيات المدمجة الجاهزة في **EMQX**، ويحافظ على أمان النظام وبساطة الهاب (ESP32) دون أي حمل إضافي على المعالج.

### مواضيع MQTT في Fisha
- حالة المشترك: `mttl/<HUB_ID>/state` (Retained)
- تنبيهات وأحداث: `mttl/<HUB_ID>/event`
- اتصال الهاب والـ LWT: `mttl/<HUB_ID>/status`
- معلومات النظام: `mttl/<HUB_ID>/info`
- إرسال الأوامر: `mttl/<HUB_ID>/cmd`
- تأكيد تنفيذ الأوامر: `mttl/<HUB_ID>/cmd/ack`

## 3. نموذج إعداد EMQX ACL (أمثلة عملية)

يمكن تطبيق هذه القواعد إما من خلال لوحة تحكم EMQX Dashboard (قسم **Access Control > Authorization**) أو عبر ملف `acl.conf`:

> **ملاحظة:** في EMQX Cloud Serverless يتم ضبط هذه القواعد من لوحة التحكم تحت **Access Control → Authorization** (topic rules per username)، وليس عبر `acl.conf`.

```erlang
%% ==========================================
%% قواعد الهاب ESP32 (Hub)
%% ==========================================
%% السماح للهاب بالنشر على مواضيع الحالة والأحداث والردود
{allow, {username, "ESP32_hub"}, publish, [
  "mttl/80F3DA40F674/state",
  "mttl/80F3DA40F674/status",
  "mttl/80F3DA40F674/info",
  "mttl/80F3DA40F674/event",
  "mttl/80F3DA40F674/cmd/ack"
]}.
%% السماح للهاب بالاستماع لموضوع الأوامر
{allow, {username, "ESP32_hub"}, subscribe, [
  "mttl/80F3DA40F674/cmd"
]}.

%% ==========================================
%% قواعد الأدمن / المسؤول (Admin Full Access)
%% ==========================================
%% صلاحيات كاملة لقراءة وإرسال جميع الأوامر
{allow, {username, "stripe_app"}, pubsub, [
  "mttl/80F3DA40F674/#"
]}.

%% ==========================================
%% قواعد أفراد العائلة (Viewer / Read-Only)
%% ==========================================
%% السماح بالاشتراك لمتابعة الحالة وقراءة القياسات فقط
{allow, {username, "family_member"}, subscribe, [
  "mttl/80F3DA40F674/state",
  "mttl/80F3DA40F674/status",
  "mttl/80F3DA40F674/info",
  "mttl/80F3DA40F674/event"
]}.
%% منع أفراد العائلة تماماً من إرسال أي أوامر
{deny, {username, "family_member"}, publish, [
  "mttl/80F3DA40F674/cmd"
]}.

%% القاعدة الافتراضية لمنع أي شيء آخر
{deny, all}.
```

## 4. التعديلات المطلوبة في تطبيق الموبايل (Fisha App)

لتوفير تجربة مستخدم متكاملة وسلسة عند استخدام حساب بصلاحيات Viewer:

1. **شاشة الاتصال (Connection Screen)**:
   - تم بالفعل دعم إدخال `Username` و `Password` منفصلين لكل جهاز وتخزينهما في إعدادات التطبيق المحلية.
   - إضافة خيار تبديل يدوي أو كشف تلقائي: "حساب للعرض فقط" (Read-Only Mode) أو "صلاحيات محدودة".

2. **التعامل مع رفض الصلاحية في MQTT**:
   - عند محاولة إرسال أمر نشر `publish` من مستخدم ممنوع عبر ACL، يقوم سيرفر EMQX برفض الرسالة (Publish Error / Not Authorized).
   - في `app_state.dart`: عند استقبال خطأ عدم الصلاحية أو عدم وصول الرد عبر `cmd/ack`، يتم إظهار رسالة للمستخدم:
     > «غير مسموح بهذا الإجراء: حسابك للمشاهدة فقط».

3. **واجهة المستخدم (UI Adjustments)**:
   - في وضع المشاهد (Viewer):
     - تعطيل مفاتيح التشغيل والإيقاف (Switches) في البطاقات والمخارج مع إظهار أيقونة قفل صغيرة.
     - إخفاء أزرار "تشغيل الكل" و "إيقاف الكل" في رأس المشترك.
     - إخفاء أو تعطيل إمكانية تعديل الجداول (Schedules)، الأتمتة (Automations)، والسيناريوهات (Scenes).
     - إبقاء شاشة قياسات الطاقة (Energy)، الحرارة، وسجل الأحداث متاحة بالكامل للقراءة الفورية والتاريخية.
